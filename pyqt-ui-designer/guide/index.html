使用说明 · 协议说明

PyQt UI Designer 使用说明

从设计界面，绑定串口、TCP 或 MQTT 数据，预览运行到导出打包的完整流程，以及下位机需要遵循的接收与发送格式。文中的示例帧和 CRC 都可以直接用于联调。

适用于 0.1.6 串口 · TCP · MQTT KEY=VALUE · JSON · HEX · Modbus RTU / TCP

用的是 FluentHMI Studio？两者工程格式相同，第 02–06 节的链路、解析、绑定、命令编码和 Modbus 规则同样适用；下载、运行和导出方式见 FluentHMI Studio 介绍。

01快速上手

以一台串口设备为例，按下面 6 步做出一个可以分发的上位机。

  1. 运行设计器从下载区获取对应平台的 zip，解压后 Windows 运行 main.exe，Mac 打开 PyQt UI Designer.app。也可以从源码运行：安装依赖后执行 python main.py（需 Python 3.10+）。
  2. 设计界面从左侧控件面板把控件拖到画布，在右侧属性编辑器修改位置、尺寸和属性。工具栏提供对齐、分布和缩放；右上角设置上位机名称和画布宽高。工程保存为 .uidp 文件。
  3. 绑定接收数据选中数值显示、LED、进度条、仪表盘等显示类控件，在属性编辑器的“数据绑定”中选择解析模式并填写绑定字段，见第 04 节。实时曲线在属性中为每条曲线单独设置。
  4. 配置发送命令选中按钮、开关、滑块、数值框或输入框，设置“发送模式”“发送内容”和“发送模板”，见第 05 节。
  5. 预览运行切换到“预览运行”页，点击“运行预览”，在画布上放置的串口、TCP 或 MQTT 配置卡片中填写连接参数并连接，直接用真实设备测试。修改设计、打开或新建工程会自动停止预览并断开连接，再次点击“运行预览”即使用当前设计。
  6. 导出与打包按 Ctrl+Shift+E（Mac 为 ⌘⇧E）或点击导航栏“导出代码”得到 Python 项目；在预览页点击“一键打包”可直接生成 exe / .app，见第 07 节。

没有硬件？从源码运行时，在仓库根目录执行 python demo/simulate.py，端口选择 DEMO 并连接，即可体验温度/压力采集、实时曲线和命令收发。

01Quick start

Using a serial device as the example, these six steps take you to a host app you can hand out.

  1. Run the designerGet the zip for your platform from the downloads. On Windows run main.exe; on a Mac open PyQt UI Designer.app. To run from source, install the requirements and run python main.py (Python 3.10+).
  2. Design the UIDrag widgets from the palette on the left onto the canvas and edit position, size and properties in the property editor on the right. The toolbar aligns, distributes and zooms; the top right sets the app name and canvas size. Projects are saved as .uidp files.
  3. Bind incoming dataSelect a display widget such as a value display, LED, progress bar or gauge, choose a parse mode under “数据绑定” (Data binding) and enter the binding field. See section 04. Live plots are configured per curve in their properties.
  4. Configure commandsSelect a button, switch, slider, spin box or line edit and set the send mode, content and template. See section 05.
  5. Run the previewSwitch to the “预览运行” (Preview) page, click “运行预览” (Run preview), fill in the connection in the serial, TCP or MQTT setup card you placed on the canvas and connect to test with the real device. Editing the design or opening or creating a project stops the preview and disconnects; click “运行预览” again to run the current design.
  6. Export and packagePress Ctrl+Shift+E (⌘⇧E on a Mac) or use “导出代码” (Export code) in the sidebar to get a Python project, or click “一键打包” (Package) on the preview page to build an exe / .app. See section 07.

No hardware? When running from source, run python demo/simulate.py in the repository root, pick the DEMO port and connect to try temperature/pressure acquisition, live plots and commands.

02链路与解析模式

设备通过画布上的串口、TCP 或 MQTT 配置卡片连接，三种链路可以同时连接，收到的数据进入同一套绑定、曲线、表格和日志。串口配置卡片设置端口、波特率、数据位、校验位、停止位和流控；TCP 和 MQTT 卡片见第 03 节。

每张卡片的“默认解析模式”决定如何把收到的数据拆成一条条消息，三种链路的选项相同，预览和导出程序使用同一套实现。

解析模式适用数据说明
line文本行每行以 LF（\n，兼容 CRLF）结束，自动识别 JSON、KEY=VALUE 和 CSV。未设置时默认使用。MQTT 的每条消息直接作为一行，不需要换行结尾。
modbusModbus RTU 响应按功能码计算帧长，CRC 校验通过后输出 reg0、coil0 等字段，见第 06 节。
modbus_tcpModbus TCP 响应按 MBAP 头里的长度切帧，没有 CRC，输出与 modbus 相同的字段，见第 06 节。
hex定长二进制帧按工程 parserConfig 中的帧头、帧尾和字段拆帧；工程本身不是 hex 模式时，使用默认帧头 AA 55、帧尾 55 AA。
项目设置—使用 .uidp 中的 serial.parser / parserConfig，三种链路共用这一份配置。

卡片上选择与工程不同的解析模式时，使用该模式的默认配置；选回“项目设置”即恢复工程配置。“HEX 字节提取”绑定直接读取收到的原始字节，不受这里的解析模式影响。

行文本自动识别（line）

收到一行文本
├─ 以 { 开头   → JSON 对象      {"temperature": 25.3}
├─ 含有 =      → KEY=VALUE      temperature=25.3,humidity=68.5
└─ 其他        → CSV            25.3,68.5,1013.2  → ch0, ch1, ch2
  • 只有实际的 LF 字节算作行尾。收到半行时等待后续数据；一次读到多行时按顺序全部处理。JSON 字符串里转义的 \n 不算换行。
  • 字段分隔符默认为逗号。数值依次尝试整数、浮点数，都失败时保留为字符串。
  • 以 { 开头但不是合法 JSON 的行会被丢弃；单行超过 64 KiB 时丢弃到下一个 LF。
  • key:value 不会被识别为键值对，请使用 key=value 或 JSON。

02Links and parse modes

Devices connect through a serial, TCP or MQTT setup card on the canvas. The three links can be connected at the same time, and their data feeds the same bindings, plots, tables and logs. The serial setup card sets the port, baud rate, data bits, parity, stop bits and flow control; the TCP and MQTT cards are covered in section 03.

Each card's “默认解析模式” (default parse mode) decides how incoming data is split into messages. All three links offer the same choices, and the preview and exported programs share the same implementation.

Parse modeDataNotes
lineText linesEach line ends with LF (\n; CRLF works). JSON, KEY=VALUE and CSV are detected automatically. This is the default. Each MQTT message counts as a line and needs no line ending.
modbusModbus RTU responsesFrame length comes from the function code. Frames that pass the CRC check produce fields such as reg0 and coil0. See section 06.
modbus_tcpModbus TCP responsesFrames are cut by the length in the MBAP header, with no CRC, and produce the same fields as modbus. See section 06.
hexFixed binary framesSplits frames by the header, footer and fields in the project's parserConfig. If the project itself isn't in hex mode, the default header AA 55 and footer 55 AA are used.
项目设置 (project)—Uses serial.parser / parserConfig from the .uidp file, one configuration for all three links.

Choosing a parse mode on the card that differs from the project's uses that mode's defaults; choosing “项目设置” again restores the project configuration. “HEX 字节提取” (HEX byte extraction) bindings read the raw bytes received and are not affected by the parse mode.

Line detection (line)

A line arrives
├─ starts with {   → JSON object    {"temperature": 25.3}
├─ contains =      → KEY=VALUE      temperature=25.3,humidity=68.5
└─ otherwise       → CSV            25.3,68.5,1013.2  → ch0, ch1, ch2
  • Only a real LF byte ends a line. Partial lines wait for more data; several lines in one read are all processed in order. An escaped \n inside a JSON string is not a line break.
  • Fields are separated by commas by default. Values are tried as integers, then floats, and otherwise kept as strings.
  • A line that starts with { but is not valid JSON is dropped; a line longer than 64 KiB is discarded up to the next LF.
  • key:value is not treated as a key/value pair. Use key=value or JSON.

03TCP 与 MQTT

TCP 配置卡片

参数说明
模式客户端：上位机主动连接设备的 IP 和端口；服务端：上位机监听端口，等待设备连入。
地址客户端模式填设备 IP 或主机名；服务端模式填本机监听地址，0.0.0.0 表示所有网卡。
端口1 ~ 65535
默认解析模式同串口；接 Modbus TCP 设备时选 modbus_tcp。
  • TCP 是字节流，半包、粘包的处理和串口相同。
  • 客户端点击“连接”后显示“连接中”，失败时卡片状态显示原因，如连接被拒绝；对方关闭连接后回到未连接状态。
  • 服务端可以同时接多个设备，状态显示当前客户端数量。每个连接单独切帧，设备之间的半包互不干扰；命令写给所有已连接的设备。“HEX 字节提取”绑定读取的是原始字节，多台设备同时发送时建议只接一台，或改用带键名的行文本 / JSON。
  • modbus_tcp 对应标准 Modbus TCP（MBAP 头，无 CRC），控件和 Modbus 卡片发出的请求自动按 MBAP 组帧；modbus 对应 Modbus RTU over TCP，带 CRC 的 RTU 帧直接走 TCP。

MQTT 配置卡片

参数说明
服务器 / 端口broker 地址和端口，默认 1883（TLS 常用 8883）。
客户端ID留空自动生成。
用户名 / 密码可选。
订阅主题一个或多个主题过滤器，用逗号、分号或换行分隔，支持 + 和 # 通配符。
发布主题所有命令都发布到这一个主题。
QoS0 / 1 / 2，订阅和发布共用。
TLS用操作系统的证书库（macOS 钥匙串、Windows 证书存储）校验 broker；自签证书需先把 CA 加入系统信任。

MQTT 传的是一条条消息而不是字节流，解析有三点不同：

  • 每条消息视为一帧。行文本模式下载荷不需要换行结尾，{"temp":25.3}、temp=25.3 都可以直接发；HEX 帧模式按主题分别缓存半包。
  • 纯数值载荷可以用主题名绑定。主题 home/temp 收到 25.3 时，解析结果为 {"ch0": 25.3, "home/temp": 25.3}，绑定字段填 home/temp 即可。带键名的行文本和 JSON 保持原样，不附加主题。
  • 命令原样发布。文本模式的换行符也会附在命令后面，发 MQTT 时一般把换行符设为“无”。

连接成功后才订阅主题。连接意外断开时卡片显示“重连中...”，重连成功后自动恢复订阅；首次连接失败（地址错误、认证失败、TLS 证书不受信任）不会重试，修正后再点“连接”。TCP 和 MQTT 卡片在“连接中”和“重连中”时都可以点“断开”取消。

多条链路同时连接

串口、TCP、MQTT 可以同时连接。各链路的数据按到达顺序分别解析后进入同一套绑定，一条链路断开不影响其他链路。命令发往每一条已连接的链路，任一链路完整写出即算发送成功，写入失败的链路会单独提示。

03TCP and MQTT

TCP setup card

SettingNotes
模式 (mode)客户端 (client): connect to the device's IP and port. 服务端 (server): listen on a port and wait for devices to connect.
地址 (address)In client mode, the device's IP or host name; in server mode, the local address to listen on, where 0.0.0.0 means every interface.
端口 (port)1 to 65535
默认解析模式 (parse mode)Same as serial; choose modbus_tcp for Modbus TCP devices.
  • TCP is a byte stream, so partial and merged packets are handled exactly as on a serial port.
  • After you click “连接” (Connect), a client shows “连接中” (connecting); a failure shows the reason on the card, such as a refused connection. When the other side closes the connection, the card returns to disconnected.
  • A server accepts several devices at once and shows how many are connected. Each connection is framed on its own, so partial frames from different devices never mix, and commands are written to every connected device. “HEX 字节提取” (HEX byte extraction) bindings read the raw bytes, so when several devices send at once, connect only one or switch to keyed line text / JSON.
  • modbus_tcp is standard Modbus TCP (MBAP header, no CRC), and requests from widgets and the Modbus card are framed with an MBAP header. modbus is Modbus RTU over TCP: RTU frames with a CRC sent straight over TCP.

MQTT setup card

SettingNotes
服务器 / 端口 (server / port)The broker's address and port; 1883 by default (8883 is usual for TLS).
客户端ID (client ID)Generated automatically when left empty.
用户名 / 密码 (username / password)Optional.
订阅主题 (subscribe)One or more topic filters separated by commas, semicolons or new lines; + and # wildcards work.
发布主题 (publish)Every command is published to this one topic.
QoS0 / 1 / 2, shared by subscribing and publishing.
TLSThe broker is verified through the operating system's certificate store (the macOS keychain, the Windows certificate store); add a self-signed CA to the system trust first.

MQTT carries messages rather than a byte stream, so parsing differs in three ways:

  • Each message is one frame. In line mode the payload needs no line ending, so {"temp":25.3} and temp=25.3 can be sent as they are. In HEX frame mode, partial frames are buffered per topic.
  • A bare number can be bound by topic. When topic home/temp receives 25.3, the result is {"ch0": 25.3, "home/temp": 25.3}, so a binding field of home/temp works. Keyed line text and JSON are left as they are, without the topic.
  • Commands are published as they are. The text-mode line ending is appended too, so set the line ending to “无” (none) for MQTT.

Topics are subscribed once the connection succeeds. If the connection drops, the card shows “重连中...” (reconnecting) and the subscriptions come back when it reconnects. A first connection that fails (wrong address, rejected login, untrusted TLS certificate) is not retried; fix the setting and click “连接” again. While connecting or reconnecting, “断开” (Disconnect) on the TCP and MQTT cards cancels the attempt.

Several links at once

Serial, TCP and MQTT can be connected together. Each link's data is parsed in arrival order and feeds the same bindings, and a link that disconnects doesn't affect the others. Commands go out on every connected link; a send succeeds once any link has written the whole command, and a link that fails to write is reported on its own.

04接收：数据绑定

显示类控件和曲线通道都通过“解析模式”从数据中取值，共四种模式。可选的“转换表达式”用变量 value 换算原始值，例如 value * 0.1。

键值匹配

按字段名从行文本解析结果中取值，适用于 KEY=VALUE、JSON 顶层字段和 CSV。MQTT 消息只有一个数值时，也可以直接填主题名，见第 03 节。

temperature=25.3,humidity=68.5
{"temperature": 25.3, "humidity": 68.5}
25.3,68.5,1013.2                → 字段名为 ch0 / ch1 / ch2
  • 解析模式键值匹配
  • 绑定字段temperature

JSON 路径

用点号分隔的路径读取嵌套 JSON，数组用下标表示。

{"data":{"sensors":[{"temp":25.3,"humi":68},{"temp":22.1,"humi":72}]}}
JSON 路径取得的值
data.sensors.0.temp25.3
data.sensors.1.humi72

HEX 字节提取

从原始字节中按偏移和数据类型取值。配置帧头和帧尾后，先截取两者之间的有效载荷，字节偏移从载荷第一个字节算起。

AA 55帧头 41 CA 66 66偏移 0 · 温度 25.3 42 89 00 00偏移 4 · 湿度 68.5 0D 0A帧尾
  • 帧头(HEX)AA 55
  • 帧尾(HEX)0D 0A
  • 字节偏移0（湿度为 4）
  • 数据类型float32
  • 字节序大端(BE)
数据类型字节数说明
uint8 / int810 ~ 255 / -128 ~ 127
uint16 / int1620 ~ 65535 / -32768 ~ 32767
uint32 / int32432 位整数
float324IEEE 754 单精度浮点
ASCII变长读到 0x00 或末尾；仅数据绑定可用，曲线不支持

连续数据流请同时配置帧头和帧尾，解析器会缓存半包并逐帧提取。只配一个或都不配时，按每次读到的字节块提取，无法推断设备的实际帧长。

Modbus

需把链路的默认解析模式设为 modbus（RTU）或 modbus_tcp（Modbus TCP）。解析器把响应帧转换为 reg0、reg1…（寄存器）或 coil0、coil1…（线圈），并附带 slave 和 fc。两种模式输出相同的字段，Modbus TCP 的单元标识符同样放在 slave，同一套绑定既能接串口 RTU 设备，也能接 Modbus TCP 设备。

01 03 06 03 E8 09 C4 00 64 02 DB
→ {"slave": 1, "fc": 3, "reg0": 1000, "reg1": 2500, "reg2": 100}
  • 寄存器索引0
  • 数据类型uint16
  • 从站过滤1（-1 为全部）
  • 功能码过滤3（-1 为全部）
  • 转换表达式value * 0.1 → 100.0

uint32、int32 和 float32 占两个寄存器。寄存器序为“大端(AB CD)”时 reg{i} 是高 16 位，“小端(CD AB)”时相反。例如 reg0 = 0x41CA、reg1 = 0x6666 按 float32 读取为 25.3。

控件如何处理数据

  • 数值显示、进度条、进度环、滑块、数值框和仪表盘会忽略无法转换为数字的值，同一帧中的其他绑定照常更新。
  • 开关接受明确的布尔文本和数值，无法识别的文本不改变状态；LED 优先使用自定义的亮灭值。
  • 开关、滑块和数值框收到设备回传的值时只更新显示，不会再次发送命令。
  • 实时曲线的每条曲线单独配置解析模式；键值匹配未填写匹配键时，用曲线名称作为键。

04Receiving: data binding

Display widgets and plot curves read values through a parse mode. There are four. The optional “转换表达式” (expression) converts the raw value with the variable value, for example value * 0.1.

Key/value (键值匹配)

Reads a field by name from a parsed line. Works with KEY=VALUE, top-level JSON fields and CSV. When an MQTT message is a bare number, the topic name works as the field too; see section 03.

temperature=25.3,humidity=68.5
{"temperature": 25.3, "humidity": 68.5}
25.3,68.5,1013.2                → fields are ch0 / ch1 / ch2
  • Parse mode键值匹配
  • Fieldtemperature

JSON path (JSON路径)

Reads nested JSON with a dot-separated path; array items use their index.

{"data":{"sensors":[{"temp":25.3,"humi":68},{"temp":22.1,"humi":72}]}}
JSON pathValue
data.sensors.0.temp25.3
data.sensors.1.humi72

HEX byte extraction (HEX字节提取)

Reads a value from raw bytes by offset and data type. With a header and footer set, the payload between them is cut out first and the offset counts from its first byte.

AA 55Header 41 CA 66 66Offset 0 · temp 25.3 42 89 00 00Offset 4 · humidity 68.5 0D 0AFooter
  • Header (HEX)AA 55
  • Footer (HEX)0D 0A
  • Byte offset0 (4 for humidity)
  • Data typefloat32
  • Byte order大端(BE) big-endian
Data typeBytesNotes
uint8 / int810 to 255 / -128 to 127
uint16 / int1620 to 65535 / -32768 to 32767
uint32 / int32432-bit integers
float324IEEE 754 single precision
ASCIIVariableUp to 0x00 or the end; data bindings only, not plots

Continuous streams: set both a header and a footer so the parser buffers partial frames and extracts them one by one. With only one or neither, values are read from each chunk as it arrives, because the real frame length can't be inferred.

Modbus

Set the link's default parse mode to modbus (RTU) or modbus_tcp (Modbus TCP). The parser turns responses into reg0, reg1… (registers) or coil0, coil1… (coils), plus slave and fc. Both modes produce the same fields, with the Modbus TCP unit identifier in slave, so one set of bindings works with serial RTU devices and Modbus TCP devices alike.

01 03 06 03 E8 09 C4 00 64 02 DB
→ {"slave": 1, "fc": 3, "reg0": 1000, "reg1": 2500, "reg2": 100}
  • Register index0
  • Data typeuint16
  • Slave filter1 (-1 for all)
  • Function filter3 (-1 for all)
  • Expressionvalue * 0.1 → 100.0

uint32, int32 and float32 span two registers. With register order “大端(AB CD)”, reg{i} holds the high 16 bits; “小端(CD AB)” is the reverse. For example reg0 = 0x41CA and reg1 = 0x6666 read as float32 give 25.3.

How widgets handle data

  • Value displays, progress bars, progress rings, sliders, spin boxes and gauges ignore values that can't be converted to numbers; other bindings in the same frame still update.
  • Switches accept explicit boolean text and numbers and ignore unrecognised text; LEDs use their custom on/off values first.
  • When a switch, slider or spin box receives a value from the device it only updates the display and does not send a command back.
  • Each plot curve has its own parse mode. In key/value mode, a curve without a key uses its name as the key.

05发送：命令配置

交互类控件用“发送模式”决定下发格式，可选文本、HEX 和 Modbus。文本与 HEX 模式下，“发送模板”中的 {value} 会替换为控件当前值。滑块和数值框可勾选“变化发送”，输入框可勾选“回车发送”。命令发往每一条已连接的链路，MQTT 发布到卡片设置的发布主题。

文本模式

控件配置实际发送

05Sending: commands

Interactive widgets pick an output format with their send mode: text, HEX or Modbus. In text and HEX modes, {value} in the send template is replaced by the widget's current value. Sliders and spin boxes can send on change (“变化发送”); line edits can send on Enter (“回车发送”). Commands go out on every connected link; MQTT publishes them to the card's publish topic.

CRC16 计算

Modbus 标准 CRC16：初值 0xFFFF，多项式 0xA001（反射形式），结果低字节在前附加到帧末。

def modbus_crc(data: bytes) -> bytes:
    crc = 0xFFFF
    for byte in data:
        crc ^= byte
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return crc.to_bytes(2, "little")

modbus_crc(bytes.fromhex("010300000003"))  # → 05 CB

Modbus TCP（MBAP）

Modbus TCP 把同样的 PDU（功能码及其后的数据）放在 7 字节 MBAP 头之后，不再附加 CRC。长度字段等于单元标识符与 PDU 的字节数之和。

事务标识符2 字节 · 大端协议标识符2 字节 · 固定 0长度2 字节 · 大端单元标识符1 字节PDU功能码 + 数据 
请求  00 01 00 00 00 06 01 03 00 00 00 03
响应  00 01 00 00 00 09 01 03 06 03 E8 09 C4 00 64
→ {"slave": 1, "fc": 3, "reg0": 1000, "reg1": 2500, "reg2": 100}

上位机发出的请求，事务标识符从 1 开始逐帧递增，65535 之后回到 0；响应里的事务标识符不参与解析。

Multi-byte fields are big-endian (high byte first); only the CRC is sent low byte first.

Both normal and exception responses must pass the CRC check. Frames that fail are dropped and do not update widgets.

Computing the CRC16

Standard Modbus CRC16: initial value 0xFFFF, polynomial 0xA001 (reflected), appended low byte first.

def modbus_crc(data: bytes) -> bytes:
    crc = 0xFFFF
    for byte in data:
        crc ^= byte
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return crc.to_bytes(2, "little")

modbus_crc(bytes.fromhex("010300000003"))  # → 05 CB

Modbus TCP (MBAP)

Modbus TCP carries the same PDU (the function code and its data) after a 7-byte MBAP header, without a CRC. The length field is the byte count of the unit identifier plus the PDU.

Transaction ID2 bytes · BEProtocol ID2 bytes · always 0Length2 bytes · BEUnit ID1 bytePDUFunction + data 
Request   00 01 00 00 00 06 01 03 00 00 00 03
Response  00 01 00 00 00 09 01 03 06 03 E8 09 C4 00 64
→ {"slave": 1, "fc": 3, "reg0": 1000, "reg1": 2500, "reg2": 100}

Requests from the host count transaction identifiers up from 1, one per frame, wrapping to 0 after 65535. The transaction identifier in a response is not used for parsing.

08常见问题

Windows 提示“Windows 已保护你的电脑”

运行包没有代码签名。点击“更多信息”，再点击“仍要运行”。

Mac 提示无法打开或无法验证开发者

运行包未做 Apple Developer ID 签名与公证。打开“系统设置 → 隐私与安全性”，在被拦截的提示处点击“仍要打开”。

Mac 上找不到串口

串口一般显示为 /dev/cu.usbserial-* 或 /dev/cu.usbmodem*。USB 转串口芯片请按厂商要求安装驱动。

连接成功但控件不更新
  • 行文本是否以 \n 结尾？没有换行时数据会一直留在缓冲区（MQTT 消息不需要换行）。
  • 默认解析模式是否和数据格式一致？Modbus RTU 选 modbus，Modbus TCP 选 modbus_tcp。
  • MQTT 的订阅主题是否覆盖设备发布的主题？只有一个数值的消息要用主题名绑定。
  • 绑定字段或 JSON 路径是否和设备发送的字段名一致？字段名区分大小写。
  • 是否写成了 key:value？请改为 key=value 或 JSON。
  • Modbus 是否设置了从站或功能码过滤？CRC 错误的帧会被丢弃。
TCP 或 MQTT 连不上

卡片状态会显示失败原因，例如连接被拒绝、用户名或密码错误。TCP 客户端请核对设备的 IP 和端口；服务端模式下，设备要连本机的 IP 和监听端口，系统防火墙也要允许连入。MQTT 启用 TLS 时请确认端口（常用 8883），broker 使用自签证书时需先把 CA 加入系统信任。“连接中”和“重连中”时可以点“断开”取消。

曲线数据会保存多少

显示缓存每条曲线最多 10,000 点，完整采样另存在临时文件中，“保存”会导出全部历史 CSV / JSON。清空曲线、停止预览或关闭控件后临时记录会释放，需要的数据请先保存。“加载”保存过的记录会以虚线叠加在实时曲线上，方便对比两次运行，“清除对比”移除叠加；“保存”只保存实时数据。

更完整的字段说明见 GitHub 上的 协议文档，问题可提交到 Issues。

08FAQ

Windows says “Windows protected your PC”

The package isn't code-signed. Click “More info”, then “Run anyway”.

macOS says the app can't be opened or the developer can't be verified

The package isn't Developer ID signed or notarized. Open System Settings → Privacy & Security and click “Open Anyway” next to the blocked app.

No serial port shows up on a Mac

Serial ports usually appear as /dev/cu.usbserial-* or /dev/cu.usbmodem*. Install the USB-serial driver your chip vendor requires.

Connected, but widgets don't update
  • Do text lines end with \n? Without it, data stays in the buffer (MQTT messages don't need one).
  • Does the default parse mode match the data? Modbus RTU needs modbus, Modbus TCP needs modbus_tcp.
  • Do the MQTT subscriptions cover the topics the device publishes to? A message that is a bare number is bound by topic name.
  • Do the binding field or JSON path match the device's field names exactly? Names are case-sensitive.
  • Is the device sending key:value? Switch to key=value or JSON.
  • Are slave or function filters set for Modbus? Frames with bad CRCs are dropped.
TCP or MQTT won't connect

The card shows why, for example a refused connection or a wrong username or password. For a TCP client, check the device's IP and port. In server mode, the device must connect to this computer's IP and listening port, and the system firewall must allow it in. With MQTT over TLS, check the port (usually 8883), and if the broker uses a self-signed certificate, add its CA to the system trust first. While “连接中” (connecting) or “重连中” (reconnecting), “断开” (Disconnect) cancels the attempt.

How much plot data is kept?

Each curve keeps up to 10,000 points on screen; the full history goes to a temporary file, and “保存” (Save) exports all of it as CSV / JSON. The temporary record is released when you clear the plot, stop the preview or close the widget, so save what you need first. “加载” (Load) draws a saved recording over the live curves as dashed lines so you can compare two runs, and “清除对比” (clear comparison) removes it; “保存” saves only the live data.

Field-by-field details are in the protocol document on GitHub (Chinese). Report problems in Issues.
